## Кейс A. «Граф денег» (русская версия ТЗ)
Источник: https://docs.google.com/document/d/1JPLU-G6R25Ge2hVaY2J9cqvrx7FGExj87XKwJPaMz3o

ТЗ кейса для HackAlem AI
Направление: Аналитика и принятие решений / Кибербезопасность и комплаенс
Формат: командная разработка, 5 часов
Данные: предоставляются в начале хакатона, обезличенные
1. Название
Граф денег: восстановление финансовой структуры организованной группы по транзакционной сети
2. Проблема
Сейчас AML-аналитик банка второго уровня сталкивается с тем, что по итогам оперативной информации ему известен только нижний уровень преступной цепочки — конкретные клиенты, получавшие деньги, связанные с незаконным оборотом наркотиков. Кто стоит выше — кто собирает эти деньги, через кого их прогоняют и кто в итоге ими распоряжается — приходится восстанавливать вручную.
Из-за чего:
Последствие
	Масштаб
	Ручная трассировка цепочки от одного клиента на 4 колена
	часы работы аналитика на один узел
	Основная часть сети остаётся невидимой
	известен 81 клиент, реальная сеть — 2 248 узлов
	Блокируется только нижний уровень
	организаторы сохраняют инфраструктуру и восстанавливают её за дни
	Решения о приоритете проверки принимаются интуитивно
	нет ранжирования, кого смотреть первым
	Эффект от решения: аналитик за минуты получает ранжированный список узлов с обоснованием роли каждого, вместо недель ручной трассировки; фокус проверки смещается с 81 «курьера» на реальные точки консолидации.
3. Пользователь
Основной пользователь: AML-аналитик / специалист подразделения финансового мониторинга банка второго уровня.
Ключевой сценарий (от входа до результата):
1. Аналитик получает от правоохранительных органов список клиентов, проходящих по делу (81 gid).
2. Загружает выгрузку исходящих переводов этих клиентов на 4 колена в инструмент команды.
3. Инструмент строит граф, считает метрики и присваивает каждому узлу роль: точка консолидации, транзит, распределитель, конечный получатель, периферия.
4. Аналитик видит схему сети с направлением потоков, подсветкой ролей и кластерами.
5. Аналитик открывает топ-лист приоритетов, читает обоснование по каждому узлу («получает от 11 разных плательщиков, отдаёт дальше 3% полученного») и формирует перечень клиентов на углублённую проверку и запрос в правоохранительные органы.
4. Задача
Разработать аналитический инструмент (пайплайн + интерфейс просмотра), который по графу транзакций определяет роли участников финансовой сети и ранжирует их по значимости, и выдаёт аналитику готовую к работе модель структуры группы: участники, связи, направление денег, транзитные узлы, точки консолидации, кластеры, ключевые узлы.
Инструмент должен отвечать на вопрос аналитика: «кого из этих 2 248 клиентов смотреть первым и почему».

Дают дополнительные баллы, сдачу не блокируют:
* Учёт артефакта обрыва графа — отделение настоящих конечных получателей от узлов, «обрезанных» 4-м коленом, с обоснованием метода.
* Временные паттерны — сквозной транзит (пришло и ушло в течение 1–2 дней), всплески активности, синхронные переводы от нескольких плательщиков в один день.
* Поиск повторяющихся маршрутов и возвратных потоков — устойчивые цепочки A→B→C и циклы, где деньги возвращаются к отправителю.
* Детекция аномалий — дробление сумм, аномальные профили узлов относительно их колена (правила или ML-модель).
* Оценка устойчивости сети — что произойдёт с сетью при изъятии топ-N узлов; распадается ли она на изолированные фрагменты.
* AI-ассистент аналитика — вопрос на естественном языке («кто собирает деньги с этих пятерых?») → ответ по графу со ссылками на узлы.
* Автогенерация карточки узла — краткая справка по клиенту: роль, потоки, связи, на что обратить внимание.
* Оценка полноты — указание, каких данных не хватает, чтобы закрыть белые пятна, и какой запрос аналитику стоит сделать следующим.
9. Ограничения
Нельзя
* Хардкодить результат — зашитые в код списки gid под «правильный ответ» вместо расчёта.
* Сдавать «чёрный ящик» — роль без объяснимого правила или интерпретируемых признаков не засчитывается (см. must have 3).
* Обогащать внешними источниками и достраивать атрибуты клиентов, которых нет в данных (пол, возраст, доход, организация) — любые такие поля будут считаться выдумкой.
* Требовать облачный кластер, GPU-обучение или платные сервисы для воспроизведения результата.

## Кейс B. ekt.kz — автоматизация формирования заказов поставщикам (русская версия ТЗ)
Источник: https://docs.google.com/document/d/1Z4faOPlT1t6NMCuJSKKB8-vkZ2LVzGMR0PO9rtZgSnM

HACKALEM AI
Информационный пакет: кейсы ТОО «Электрокомплект» (ekt.kz)
Партнёр: ТОО «Электрокомплект» (ekt.kz). 
Кейс. Автоматизация формирования заказов поставщикам
1. Название
	Автоматический расчёт заказов поставщикам для пополнения склада
	2. Проблема и ценность
	Сейчас менеджер отдела закупа рассчитывает потребность в пополнении склада вручную, консолидируя данные в Excel. Из-за трудоёмкости такого детального анализа расчёт проводится нечасто и не в режиме реального времени, из-за чего возникают избыточные запасы по одним позициям и дефицит по другим, а разовые крупные заказы (в том числе продажи большого объёма одному клиенту) искажают расчёт регулярной потребности, что ведёт к лишним издержкам на хранение и упущенным продажам.
Ценность решения: снижение издержек на избыточное хранение, сокращение случаев дефицита и упущенных продаж, повышение точности регулярных закупочных решений.
	3. Пользователь
	Основной пользователь: менеджер отдела закупа.
Ключевой сценарий: запускает расчёт по складу или категории → получает список рекомендованных заказов поставщикам с обоснованием по каждой позиции → проверяет, корректирует при необходимости → утверждает заказ.
	4. Задача
	Разработать сервис, который на основе истории продаж, сезонности, устойчивого роста спроса, текущих остатков, информации по товарам в пути, категорий товаров, прогноза по приросту и оценки упущенного спроса в периоды отсутствия товара формирует рекомендованные заказы поставщикам.
Сервис должен выявлять разовые крупные заказы (включая крупные продажи одному клиенту) и исключать их из расчёта регулярной потребности в запасах.
	5. Вход → выход
	Вход: история продаж (дата, артикул, количество, обезличенный клиент, цена) за период, текущие остатки по складам, периоды отсутствия товара (stockout) по артикулам, справочник поставщиков и сроков поставки, материальная ведомость из 1С.
Выход: список рекомендованных заказов (артикул, поставщик, рекомендуемое количество, обоснование, срочность) в виде таблицы/дашборда с возможностью экспорта.
	6. Данные (если задача на основе данных)
	Ссылка/способ доступа: выгрузка истории продаж и остатков; партнёр предоставит отчёт V2 и данные по динамике продаж (образец предоставляется партнёром, полный набор и точная дата выдачи — по согласованию).
Поля и объём: дата продажи, артикул, наименование, количество, цена, обезличенный ID клиента, склад, остаток на дату; история продаж за продолжительный период (порядок объёма уточняется партнёром).
Ограничения: данные о клиентах должны быть обезличены; допустимо использование синтетических данных с реалистичным распределением для разработки и тестирования.
	7. Must have
	1) Расчёт базовой потребности в пополнении по каждому артикулу с учётом всех предусмотренных данных (история продаж, текущие остатки, товары в пути, категории товаров, прогноз по приросту) — проверка: на тестовом наборе данных формируется корректный список позиций с рекомендуемым количеством, и расчёт не игнорирует ни один из переданных источников данных — изменение любого из них (например, объёма товаров в пути) отражается на итоговом результате.
2) Учёт сезонности и устойчивого роста спроса при прогнозировании — проверка: для товара с выраженной сезонностью прогноз отражает сезонный паттерн, а не просто среднее значение по всей истории.
3) Оценка и компенсация упущенного спроса в периоды отсутствия товара — проверка: для артикула с зафиксированным stockout расчётная потребность скорректирована в большую сторону по сравнению с расчётом по «сырым» фактическим продажам.
4) Выявление и исключение разовых крупных заказов, включая крупные продажи одному клиенту — проверка: искусственно добавленный в тестовые данные разовый крупный заказ не приводит к существенному росту рекомендуемого регулярного количества.
5) Формирование итогового списка заказов, сгруппированного по поставщикам, с кратким обоснованием по каждой позиции — проверка: каждая строка выходного списка сопровождается объяснением, почему предложено именно такое количество, и список можно просмотреть в разбивке по каждому поставщику.
	8. Опционально
	Приоритизация позиций по риску дефицита; учёт минимальной партии заказа и условий конкретного поставщика; визуализация трендов спроса по категориям; автоматическая выгрузка/рассылка сформированного заказа поставщику.
	9. Ограничения
	Нельзя: автоматически отправлять заказ поставщику без подтверждения ответственного сотрудника; использовать в расчётах неанонимизированные данные о клиентах.
Обязательно учесть: приватность данных о продажах и клиентах, объяснимость расчёта, устойчивость алгоритма к аномалиям и выбросам во входных данных, совместимость выходного формата с текущей учётной системой компании.
