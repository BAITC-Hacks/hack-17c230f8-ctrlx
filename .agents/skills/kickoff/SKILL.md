# Kickoff: ТЗ → план на 5 часов для трёх человек и их агентов

Команда — Мустафа, Амирхан, Ансар (строки `MEMBER` в `docs/ZONES.md`: id, имя, GitHub). Кто чем занят, решаешь здесь: по ТЗ и по сильным сторонам из `docs/TEAM.md`. Цель — за 15–20 минут получить план, по которому три агента работают параллельно и не лезут в файлы друг друга. Продуктовый код не пиши. Думай тщательно: ошибка здесь стоит всех пяти часов.

1. Прочитай `docs/TASK.md` целиком и файлы в `data/`, если есть. ТЗ пустое → остановись и попроси вставить. Трек «Финансы» → прочитай `docs/DOMAIN-FINANCE.md` (кто кейсодатели, регуляторика, открытые данные, метрики, паттерны архитектуры, обзор типовых сценариев): опирайся на него в углах решения и вопросах, но идею бери из ТЗ, а не из обзора.
   **Решаем ровно один кейс** (инструкция организаторов). В `docs/TASK.md` несколько кейсов → до шага 3 выведи таблицу: кейс · критерии и баллы · есть ли данные · демо-эффект · главный риск за 5 часов · совпадение с сильными сторонами команды → порекомендуй один; выбирают люди. Дальше работай только с выбранным, остальные удали из `docs/TASK.md`.
2. Прочитай `docs/TEAM.md`. Если у Амирхана или Ансара не заполнены сильные стороны и агент — спроси это в первом раунде шага 3 и впиши ответ.
3. **Понимание и развилки — не дольше 12 минут (до ~13:22):**
   - **Как я понял ТЗ** — 4–6 строк в чат: цель партнёра, кто пользователь, что считается успехом; отдельно — что прямо сказано в ТЗ, а что твои допущения. Команда поправит.
   - **Совет агентов** (≤ 4 мин, параллельно): пока люди читают твоё «как я понял», запусти одновременно 4 субагента. Каждому дай путь к `docs/TASK.md`, `docs/TEAM.md`, §0 `docs/DOMAIN-FINANCE.md` и одну роль:
     1. **Кейсодатель** — какая боль партнёра самая дорогая, что он внедрил бы после пилота, какие данные и нормы важны;
     2. **Жюри** — что по критериям ТЗ даёт максимум баллов, чем решение запомнится среди сотен команд, какая «вау»-демонстрация укладывается в 60 секунд;
     3. **Архитектор** — что реально сделать втроём за 4 часа: MVP-срез, данные, стек, где риски интеграции;
     4. **Скептик** — как это провалится (данные, LLM, запуск у эксперта по README, время) и что упростить.
     Каждый предлагает 1–2 идеи решения и оценивает их, не больше 12 строк. Субагентов нет (Codex) — пройди те же 4 роли сам, по очереди.
   - **Три угла решения** из совета — таблицей: ценность для партнёра · вау · уникальность · риск · успеваем за 5 часов, оценки 1–5. Порекомендуй один и привей к нему лучшие находки двух других; выбирают люди.
   - **Grill по процедуре скилла `grilling`**, но в лимите хакатона: максимум 2 раунда, до 7 вопросов в раунде, у каждого — твой рекомендованный ответ. Факты (формат данных, что в `data/`, что в ТЗ, что в репо) выясняй сам — не спрашивай. Команда отвечает вслух, лид печатает коротко («1 ок, 2 — B, 3 ок»). Что не решено к 13:22 — в «Допущения» с твоим выбором по умолчанию, и дальше.
4. Заполни `docs/REQUIREMENTS.md` по шаблону:
   - **Карта баллов**: критерий из ТЗ → баллы → чем берём → как эксперт проверит. Критериев нет → рубрика репетиции: соответствие кейсу 20, техреализация 25, README 20, воспроизводимость 20, надёжность 15.
   - **Требования R1..Rn**: must/should/could; формулировка из ТЗ; приёмка «вход → ожидаемый выход»; владелец (id). Must — всё, без чего ТЗ не выполнено.
   - **Контракт** — то, что позволяет работать параллельно: модели данных (поля, типы), эндпоинты API (метод, путь, запрос → ответ, ошибки), форматы файлов, пример JSON на каждый. Формат задан в ТЗ — повторяй буквально. Остальные работают по контракту на моках, пока лид его реализует.
   - **Шов для тестов** — один, как можно выше: главный API-эндпоинт или CLI. Тесты основного сценария идут через него, а не через внутренности; это же проверяет `scripts/smoke.sh`.
   - **Допущения** и вопросы к организаторам. **MVP-срез**: что готово к 15:50; что — если останется время; что точно НЕ делаем.
   - **Стек**: `web` или `py`, только один. Данные/ML/скоринг/пакетная обработка → `py`; чат/воркфлоу/дашборд/много UI → `web`. Обоснование в 2 строки.
   - **Данные и хранение** (эксперт запускает по README без наших аккаунтов, п. 5.6.6): данные ТЗ — в `data/` (файл ≤ 50 МБ; больше — выборка в репо + команда загрузки полного набора), чтение — pandas/DuckDB, запись — SQLite или JSON. Облачная БД (Supabase: `.env.local`, `scripts/db-check.sh`) — только если демо обязано сохранять данные между запросами, и всегда с локальным фолбэком. Модель — обучаем офлайн (`uv add scikit-learn lightgbm duckdb`, кэш прогрет), в репо — скрипт обучения, артефакт ≤ 50 МБ и метрики в `docs/METRICS.md`, чтобы инференс работал сразу после clone; для web-демо модель экспортируем в JSON/ONNX и считаем в Next.js.
   - **Потоки работы** — ровно три, под это ТЗ (например: ядро+API+LLM · интерфейс и демо-сценарий · данные+тесты+README; для ML-задачи иначе: данные и признаки · модель и метрики · API/UI и README). Назначь каждому человеку по потоку по сильным сторонам и объясни одной строкой. Лид дополнительно держит контракт и интеграцию. Владелец README, `tests/`, `scripts/smoke.sh`, `docs/TESTING.md` и сдачи на платформе — один человек.
   - **План по часам**: результат каждого к checkpoint 13:45, 14:45, 15:45, 16:45 и фриз в 16:30.
   - **Риски** (≤5) со страховкой. **Одна «вау»-идея** (уникальность и польза для партнёра) — только после всех must. Репо читают все участники: вау-идею и три угла решения в файлы не пиши — отправь их в канал `scripts/msg.sh all "[IDEA] …"` (он приватный); в README и код она попадает после 16:00.
5. **Зоны** в `docs/ZONES.md`: строки `mustafa: …`, `amirkhan: …`, `ansar: …` (префиксы путей через пробел) без пересечений — у каждого существующего и будущего файла один владелец. Контракт (`lib/types.ts` | `app/schemas.py`), `AGENTS.md`, `docs/REQUIREMENTS.md`, `docs/ZONES.md` — лиду. Строки `MEMBER`, `LEAD`, `ALL` не трогай, если лид не попросил сменить лида.
6. **Задачи** в `docs/tasks/<id>.md`: в «Сейчас» — первая задача, в «Дальше» — 2–4 следующих. Формат: «R-ID — цель · файлы · что нельзя трогать · готово, когда (команда проверки или наблюдаемый результат)». Первые задачи не должны ждать лида: интерфейс — на моках контракта, данные и тесты — по контракту.
7. Обнови шапку `AGENTS.md` (название, одна фраза, трек).
8. Выведи в чат: стек и команду `../toolkit/bootstrap.sh web|py`; must-список; кто какой поток ведёт и почему; зоны; первые задачи каждого — готовые к копированию в их агентов.
9. `ZONE_OK=1 scripts/checkpoint.sh "kickoff: requirements, contract, streams, zones, tasks"`, затем `scripts/msg.sh all "kickoff готов: git pull → scripts/sync.sh, задачи в docs/tasks/<id>.md"` и скажи Амирхану и Ансару то же голосом.
